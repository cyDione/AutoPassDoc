**选型理由**

| 选择 | 理由 |
|---|---|
| Tauri 2 | 安装包小（约 10 MB 级）、内存低；一套代码出 Windows / macOS；后端 Rust 适合重计算 |
| Rust 后端做文档引擎 | 22 万字文档的解析、diff、检索都在 Rust 完成，前端只负责显示 |
| React + TS | 生态成熟，虚拟列表、diff 展示组件现成 |
| SQLite | 单人本地使用，零运维，一个文件便于导出/备份 |
| 本地 OpenAI 兼容服务 | 小模型用 Ollama、Xinference 等在本机运行，软件按普通服务商接入，不把推理运行时打进安装包 |

## 3. 文档引擎（docx-engine）

### 3.1 设计原则：只改动过的地方，其余字节原样保留

.docx 是一个 zip 包，正文在 `word/document.xml`。常见做法是"解析成对象 → 改 → 整体重新序列化"，这会悄悄丢掉引擎不认识的标签（域代码、自定义 XML、WPS 扩展等），破坏保真。

本引擎采用**补丁式写回**：

1. 解析时，为每个段落 `<w:p>` 记录它在原始 XML 中的**字节区间**。
2. 修改只发生在段落级：被修改的段落重新生成 XML，其余段落直接拷贝原始字节。
3. zip 中未改动的文件（图片、样式、页眉页脚等）**原样拷贝**，不解压不重压。

结果：未修改的部分与原文件逐字节一致（需求 P-4）。

### 3.2 文档模型

```
Document
├─ blocks: Vec<Block>              // 顺序排列
│   ├─ Paragraph { id, style, outline_level, runs, byte_span, char_range }
│   ├─ Table     { id, rows → cells → blocks, byte_span }
│   └─ Other     { byte_span }     // 引擎不认识的块，原样保留
├─ comments: Vec<Comment>
├─ styles, numbering（仅解析显示所需部分）
└─ text_index                      // 全文字符偏移 → 段落/run 的映射，用于定位和搜索
```

- `Run` 保存文本和原始 `rPr`（字符格式）XML，改写时插入的文字继承所在位置 run 的格式。
- `char_range` 是段落在全文中的字符区间，批注锚点、搜索结果、知识库引用都用字符偏移表示。
- 解析使用 `quick-xml` 流式读取，不构建 DOM，22 万字文档目标 < 1 秒。

### 3.3 批注

| 文件 | 内容 |
|---|---|
| `comments.xml` | 批注 id、作者、缩写、时间、内容 |
| `document.xml` | `commentRangeStart` / `commentRangeEnd` 标出批注覆盖的原文范围 |
| `commentsExtended.xml` | 回复关系（`paraIdParent`）、是否已解决（`done`） |
| `commentsIds.xml` / `commentsExtensible.xml` | 持久 id、UTC 时间（新版 Word 使用） |

解析后每条批注得到：作者原始署名、锚定的字符区间、回复链、解决状态。

**写回操作**：

- 标记已解决：设置 `commentsExtended.xml` 中 `w15:done="1"`。
- 追加回复：新建一条批注，并用 `paraIdParent` 指向原批注。
- 作者改名写回（可选，需求 R-6）：修改 `comments.xml` 中的 `w:author`。

### 3.4 修订写回（默认模式）

AI 修改应用时，先对"原文片段 ↔ 新文本"做**字级 diff**（中文按字，英文和数字按词），然后：

- 删除的部分：原 run 拆分，被删字符包进 `<w:del><w:r><w:delText>…`
- 新增的部分：`<w:ins><w:r>…`，继承相邻 run 的格式
- 作者写"AutoPassDoc"，也可在设置里改成用户自己的名字；时间为当前 UTC

"直接替换"模式则只替换 run 中的文字，不加修订标记。

### 3.5 已有修订

原文中已有的 `<w:ins>` / `<w:del>` 会被解析并在视图中显示为修订样式；AI 修改的片段如果与已有修订重叠，**提示用户先处理已有修订**（第一版不做嵌套修订）。

### 3.6 保存

- 默认**另存为新文件**（`原文件名_AutoPassDoc.docx`），避免覆盖原稿；设置中可改为覆盖保存。
- 保存流程：写临时文件 → 校验能重新解析 → 原子替换，防止中途崩溃损坏文件。

## 4. 大文档性能

**目标**（需求 P-3）：22 万字、500 条批注的文档，打开 < 3 秒，滚动 60fps，批注定位即时。

| 环节 | 做法 |
|---|---|
| 解析 | Rust 流式解析，后台线程执行，完成前先显示进度 |
| 传输 | 前端只按可视区域请求段落范围（每次约 200 段），不把整篇文档一次性塞进 WebView |
| 渲染 | 虚拟滚动（TanStack Virtual），只渲染可视区附近几十个段落；段落高度先估算后测量缓存 |
| 定位 | 批注 → 段落索引由后端直接给出，前端滚动到该索引即可 |
| 搜索 | 在 Rust 侧对 `text_index` 搜索，前端只收结果列表 |
| 图片 | 按需解出，通过 Tauri 自定义协议加载，不转 base64 |

**显示方式说明**：视图采用**流式版式**（类似 Word 的"Web 版式 / 阅读视图"），显示标题、段落、列表、表格、图片、批注和修订，**不做分页排版**。分页排版的代价极高，且与"按批注改稿"的核心任务无关；最终版式仍以 Word 打开为准。

**性能测试**：`testdata/` 下用脚本生成 22 万字、500 条批注、含表格和图片的文档，CI 中跑解析和保存的基准测试，防止性能回退。

## 5. 模型适配层（models）

### 5.1 四个统一接口

```rust
trait ChatModel      { async fn generate(&self, req: ChatRequest) -> Result<ChatResponse>; /* + 流式 */ }
trait DecisionModel  { async fn decide(&self, state: &str, questions: &[Question]) -> Result<Vec<Answer>>; }
trait Embedder       { async fn embed(&self, texts: &[String]) -> Result<Vec<Vec<f32>>>; }
trait Reranker       { async fn rerank(&self, query: &str, docs: &[String]) -> Result<Vec<f32>>; }
```

`Question` 分三种：`Noul`（是/否）、`Choice`（选项）、`Score`（打分），`Answer` 均带概率。

### 5.2 服务商适配

| 服务商类型 | Chat | Decision | Embedding | Rerank | 拉取模型列表 |
|---|---|---|---|---|---|
| OpenAI 兼容（DeepSeek、通义、智谱、Kimi、硅基流动、vLLM、LM Studio 等） | ✓ | | ✓ | ✓（如支持） | `GET /v1/models` |
| Anthropic | ✓ | | | | `GET /v1/models` |
| OpenRouter | ✓ | ✓（Jev，Decisions API） | ✓ | | `GET /api/v1/models`（含上下文长度、支持的参数） |
| Cloudflare Workers AI | | ✓（Jev） | ✓ | ✓ | 模型目录接口 |
| TypeSafe 官方 | | ✓（Jev） | | | — |
| Ollama | ✓ | | ✓ | | `GET /api/tags` + `POST /api/show`（含上下文长度） |
| 本地 ONNX | | ✓（Laya） | ✓（bge-m3） | ✓（bge-reranker-v2-m3） | 本地模型目录 |

> Jev 走专门的 Decisions API，不是聊天接口，请求/响应格式在实现 M2 时按官方文档核对。

### 5.3 能力描述与自适应（需求 M-4）

每个已添加的模型保存一份能力描述：

```
ModelProfile {
  context_window, max_output_tokens,
  reasoning: None | Levels(["low","medium","high"]) | Budget { min, max },
  structured_output: bool, tool_use: bool,
  source: Fetched | BuiltIn | Manual     // 能力从哪来
}
```

- **来源优先级**：用户手动填写 > 接口返回 > 内置已知模型表 > 默认值。用户改过的值在重新拉取模型列表后仍保留。
- **思考强度**：UI 只显示该模型支持的档位；适配层把统一的档位映射到各家参数（如 `reasoning_effort`、`reasoning.effort`、思考预算、`enable_thinking`）。
- **上下文预算**：组装提示词时按优先级填充，直到占满上下文的 70%（其余留给输出）：
  1. 系统指令 + 批注 + 被批注原文（必须）
  2. 审稿人画像
  3. 所在段落及前后段落
  4. 知识库片段（按重排分数）
  5. 该审稿人的相似历史案例
  6. 所在章节的更多上下文

### 5.4 本地小模型（需求 M-5 ~ M-7）

实际实现与 v0.1 设计不同：**没有把 ONNX Runtime 内嵌进软件**，小模型通过本机运行的 OpenAI 兼容服务接入，和远程服务商走同一套代码。

| 模型 | 推荐的本地运行方式 | 在软件里怎么配 |
|---|---|---|
| bge-m3（向量） | Ollama（`ollama pull bge-m3`）、Xinference、LM Studio | 服务商类型选 Ollama 或 OpenAI 兼容，地址填 `http://localhost:11434` 等 |
| bge-reranker-v2-m3（重排） | Xinference、vLLM、text-embeddings-inference（提供 `/rerank` 接口） | OpenAI 兼容，重排路径按服务填写（默认 `rerank`） |
| Laya（决策） | 需要一个实现 Jev `systemone` 接口的本地服务；目前没有现成的 | 决策模型也可以改用"聊天模型评判"模式，用本地大模型回答同样的问题 |

原因：ONNX 内嵌需要在 Windows/macOS 各自打包推理库和模型，体积大；本地服务方案零额外代码，用户已有 Ollama 时开箱即用。**ONNX 内嵌推理和 Laya 本地运行都没有实现，也没有测试**，如以后确有需要再做。

### 5.5 Key 安全

API Key 通过 `keyring` crate 存入 Windows 凭据管理器 / macOS 钥匙串，SQLite 中只存引用。系统凭据库不可用时（以及 Linux 开发环境），退回到数据目录下仅当前用户可读的 `secrets.json`。Key 不会出现在日志、导出数据和错误信息中。

## 6. AI 修复流程（core）

```
点击"AI 修复"
  │
  ├─ 1. 收集上下文：批注、锚定原文、所在段落与前后段落、标题路径
  ├─ 2. 检索：知识库 Top-K（查询 = 批注 + 原文）、审稿人画像、该审稿人最相似的 3 条历史案例
  ├─ 3. 生成：大语言模型输出结构化结果 { 修改后文本, 修改说明, 引用片段 id 列表 }
  │        约束：只改批注锚定的段落，改动尽量小
  ├─ 4. Diff：字级 diff，前端显示删改
  ├─ 5. 评判：决策模型回答一组问题 → 各项概率 → 加权得综合置信度
  ├─ 6. 展示：diff + 置信度 + 各项结果 + 引用文件（可点击跳转）
  └─ 7. 用户操作：应用 / 编辑后应用 / 重新生成 / 忽略
            └─ 应用 → 修订写回 → 批注标记已解决（可选追加回复）→ 写入撤销栈 → 记录反馈
```

**评判问题（默认，可配置）**

| 问题 | 类型 | 权重 | 通过条件 |
|---|---|---|---|
| 回应批注：修改是否切实解决了批注提出的问题？ | 是/否 | 0.4 | P(是) ≥ 阈值 |
| 保持原意：是否保留了原文核心意思和关键信息？ | 是/否 | 0.25 | P(是) ≥ 阈值 |
| 有据可查：新增的事实、数据、文号是否都能在原文、批注或参考资料中找到依据？ | 是/否 | 0.25 | P(是) ≥ 阈值 |
| 公文规范：表述是否符合公文写作规范？ | 打分 1~5 | 0.1 | 期望分 ≥ 3.5 |
| 问题类型（不计分，用于审稿人画像） | 选项 | — | — |

v0.2：四个问题都改成"是 = 好"的问法，便于决策模型校准。用"【待补充：…】"标出的待补充内容不算编造。决策模型默认走 Jev 的 `systemone` 接口；没有 Jev 时可在设置中改成"聊天模型评判"，让大语言模型回答同样的问题并给出概率。没有配置决策模型时仍可生成修改，但不给置信度。

综合置信度 = 各项加权；**任一硬性项未通过则不允许一键应用**，即使综合分达标。阈值默认 0.8，可按审稿人调整。

**批量修复**：同一审稿人的多条批注并发生成（并发数可配），结果逐条出现在侧栏，用户逐条或批量应用。

## 7. 知识库（kb）

> v0.2：实现改用 **SQLite FTS5 + 向量**，不再用 Tantivy / LanceDB。一个知识库就是一个文件夹（`kb.sqlite` + `files/` 原文件副本），备份、迁移只需复制文件夹。实测 2 万个片段时：关键词检索 0.1～31 ms，向量检索约 6 ms，混合检索约 37 ms（release 构建）。

### 7.1 导入流程

```
文件 → 解析（docx 用自家引擎，pdf 抽文字层，txt/md 直读，自动识别 GBK/UTF-8）
     → 结构识别（第X章/节/条、一、（一）1.（1）等编号，Word 和 Markdown 标题样式）
     → 元数据提取（标题、文号、发文机关、成文日期；识别不到或识别错可手动改，改过的不会被重新导入覆盖）
     → 分块（父块 = 条/节，子块 ≤ 约 400 字；标题文字保留在块内，不丢任何文字）
     → 索引（子块进 FTS5 关键词索引，jieba 分词；文号、标题、发文机关单独一列，权重较低）
     → 向量（后台用配置的向量模型分批生成，可随时中断，下次接着做）
```

- 按文件内容哈希判断：同一内容再次导入直接跳过；同一路径的文件改过后重新导入，替换旧版本并保留 id。
- 扫描版 PDF（无文字层）提示"需要 OCR"，暂不处理。个别使用预定义中文编码的 PDF 页面无法提取，会提示是哪一页。

### 7.2 检索流程

1. 子块双路召回：FTS5 BM25（jieba 分词）Top 50 + 向量余弦 Top 50（向量常驻内存，i8 量化缓存）
2. RRF 融合排序；查询里出现某份文件的文号时，该文件排第一
3. 配置了重排模型时，对前 30 条重排
4. 子块 → 父块（条/节）扩展，同一条下的多个子块去重后交给大语言模型
5. 每个结果带 `{文件, 标题路径, 字符区间}`，AI 修复结果里显示为可点击的引用

没有配置向量模型、或还没生成向量时，只用关键词检索，并在结果里提示。

### 7.3 引用跳转（需求 K-6）

点击引用 → 用系统默认程序打开知识库里保存的原文件副本（原文件移动或删除后仍可打开）。软件内定位高亮留待后续。

## 8. 审稿人画像（core）

### 8.1 数据

| 表 | 内容 |
|---|---|
| `reviewers` | 审稿人：姓名、备注、个人阈值 |
| `reviewer_aliases` | 署名映射：批注作者原始署名 + 缩写 → 审稿人（需求 R-6） |
| `cases` | 每次修复：审稿人、批注、原文、AI 输出、最终应用文本、评判结果、用户操作（采纳 / 编辑后采纳 / 拒绝）、问题类型 |
| `profiles` | 画像摘要，带版本号 |

### 8.2 作者识别与改名

- 导入文档时按署名 + 缩写查 `reviewer_aliases`，命中则自动归属；未命中的署名在侧栏标"未识别"。
- 用户在批注上选择"归到已有审稿人"或"新建审稿人"，映射写入 `reviewer_aliases`，之后自动生效。
- "Administrator""user"这类通用署名，映射**只对当前文档生效**，避免把不同人混在一起。

### 8.3 画像提炼

- 问题类型：用决策模型的"选项"题给每条批注分类（数据口径、政策依据、措辞规范、格式、逻辑结构、其他）。
- 每新增 10 条案例，用大语言模型重新总结一次画像：关注点排序、偏好表述、常见要求，保存新版本。
- 修复时注入：画像摘要 + 该审稿人最相似的 3 条"批注 → 最终采纳文本"作为示例（v0.2 用字符二元组相似度挑选，不依赖向量模型）。
- 提炼频率可在设置中改；审稿人页面也可以随时手动提炼。

### 8.4 Laya 校准与微调（后续）

`cases` 表中"采纳 / 拒绝"即是评判模型的标注数据。积累后：先做温度校准（便宜、立即见效），数据量足够再微调 Laya。第一版只负责**记录数据并支持导出**：设置 → 数据 → 导出评判数据集，每行一条 JSON（批注、修改前后、最终文本、采纳/编辑后采纳/拒绝、标签 1/0.5/0、当时的评判结果），训练流程放在后续。

### 8.5 按审稿人预审（需求 M5 扩展，已实现）

选一位审稿人和一段文档（如某一章），大语言模型根据他的画像和以往批注，预测他会在哪些地方提出什么批注（逐字摘录原文定位 + 批注内容 + 问题类型）。文档超过模型上下文时自动分批，最多 8 批。还没有画像也没有历史批注的审稿人会提示先积累记录。

## 9. 存储

- 应用数据目录：`%APPDATA%\com.autopassdoc.desktop`（Windows）/ `~/Library/Application Support/com.autopassdoc.desktop`（macOS）
- `app.db`（SQLite）：设置、服务商与模型能力、审稿人与署名映射、修复案例、画像（撤销历史只在内存中，随文档关闭清空）

- `secrets.json`：仅在系统凭据库不可用时使用
- 换电脑：复制整个应用数据目录即可（API Key 在系统凭据库中，需要重新填写）；一键打包导出/导入尚未实现
