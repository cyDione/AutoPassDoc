## 1. 背景与目标

报告写完后要交给多位专家审阅，每轮都会返回大量 Word 批注，需要反复逐条修改。AutoPassDoc 的目标是：

1. **把"按批注改稿"这件事自动化**：AI 读懂批注和上下文，给出修改建议，人确认后写回原文。
2. **越用越懂审稿人**：按批注作者积累其关注点和修改偏好，下次同一位专家的批注能改得更准，甚至提前按他的习惯预审。
3. **有据可依**：修改时能引用用户导入的政府文件、通告等资料，避免"AI 自己编"。
4. **大文档不卡**：22 万字以上的报告打开、滚动、定位批注都要流畅。

## 2. 功能需求

| D-5 | 批注侧栏 | 按位置排列，点击批注定位到原文并高亮；可按作者、状态（未处理/已修复/已忽略）筛选 |

### 2.2 AI 修复（P0）

| 编号 | 需求 | 说明 |
|---|---|---|
| A-1 | 批注上的"AI 修复"按钮 | 每条批注一个按钮；支持批量修复（选中多条 / 某位作者的全部） |
| A-2 | 上下文组装 | 批注内容 + 被批注原文 + 所在章节上下文 + 相关知识库片段 + 该作者的风格画像 |
| A-3 | Diff 预览 | 以"删除线红色 / 新增绿色"展示修改前后对比，支持字级 diff |
| A-4 | 置信度评审 | 用决策模型（Jev / Laya，见 4.3 节）对修改做一组结构化判断，每项输出校准过的概率：是否回应了批注、是否改变原意、是否引入原文和知识库之外的事实、表述规范性评分 |
| A-5 | 阈值与应用 | 综合置信度达到阈值才允许一键应用；低于阈值时显示是哪一项没通过，可重新生成或手动编辑后应用 |
| A-9 | 引用出处 | AI 生成的修改旁边列出所引用的知识库文件名和条款，点击直接打开（见 K-6） |

| A-7 | 批注状态回写 | 应用后可把批注标为"已解决"，或自动追加一条回复说明改了什么 |
| A-8 | 撤销 | 应用后可撤销，保留完整操作历史 |

### 2.3 审稿人画像与持续学习（P1）

| 编号 | 需求 | 说明 |
|---|---|---|
| R-1 | 按作者归档批注 | 自动识别批注作者，建立审稿人档案；支持合并同一人的不同署名 |
| R-2 | 记录"批注 → 最终采纳的修改"样本 | 用户采纳、修改后采纳、拒绝，都作为反馈信号 |
| R-3 | 风格画像提炼 | 定期把该作者的历史样本总结成画像：常关注的问题类型（数据口径、政策依据、措辞规范、格式等）、偏好的表述方式 |
| R-4 | 修复时注入画像 | 遇到该作者的新批注时，把画像 + 最相似的历史样本作为示例一并提供给模型 |
| R-5 | 按作者预审（P2） | 在发给某位专家前，模拟他的视角先扫一遍全文，提前标出他大概率会批的地方 |
| R-6 | 批注作者改名 / 新建 | 批注署名不是真实姓名时（如"Administrator""user""未知"），可在批注上把作者改为已有的审稿人，或新建一位审稿人。系统记住"署名 → 审稿人"的映射，下次同一署名自动归到同一人；可选择是否把真实姓名写回 .docx 的批注作者字段（默认不写回，只在软件内映射） |

> 说明：这里的"蒸馏"建议先用**画像 + 检索历史样本（few-shot）**实现，不需要真的微调模型。样本积累到一定规模后，再评估是否做微调。

### 2.6 模型接入（P0）

所有模型都采用 **BYOK（用户自带 API Key）**，软件本身不绑定任何模型厂商。

| 编号 | 需求 | 说明 |
|---|---|---|
| M-1 | 四类模型分别配置 | 大语言模型（生成修改）、决策模型（Jev / Laya，评判置信度）、向量模型、重排模型，各自选择服务商和模型 |
| M-2 | 服务商接入 | 支持 OpenAI 兼容接口（覆盖 DeepSeek、通义千问、智谱、Kimi、硅基流动、OpenRouter 等）、Anthropic、Cloudflare Workers AI（Jev）；本地服务支持 Ollama、LM Studio、vLLM 等 OpenAI 兼容端点 |
| M-3 | 拉取模型列表 | 填入地址和 Key 后，一键拉取该服务商可用的模型列表供选择 |
| M-4 | 能力自适应 | 拉取时读取模型能力：上下文长度、最大输出长度、是否支持思考（推理强度档位）、是否支持结构化输出。软件据此自动调整：上下文放多少章节和知识库片段、思考强度下拉框显示哪些档位、长文本是否需要分段。接口拿不到的能力可手动填写 |
| M-5 | 小模型本地运行 | 向量模型、重排模型、Laya 这类小模型（几亿参数级）可以直接在本机运行，不需要联网，也不需要单独部署服务 |
| M-6 | 本地模型管理 | 在软件内下载、切换、删除本地模型；显示模型大小和是否可用 GPU 加速 |
| M-7 | 离线模式 | 本地模型齐全时，除大语言模型外的功能都可离线使用；大语言模型也可指向本机 Ollama 等服务，实现全流程离线 |
| M-8 | Key 安全 | API Key 存入系统凭据库（Windows 凭据管理器 / macOS 钥匙串），不明文落盘 |

## 4. 技术方案建议

### 4.1 整体架构

- **桌面框架：Tauri 2 + Rust 后端 + Web 前端（React/TypeScript）**。安装包小、内存占用低，一套代码可构建 Windows 和 macOS。
- **文档引擎（Rust）**：流式解析 document.xml，建立"段落 → 字符偏移"索引；修改时只替换受影响的 XML 节点，其余字节原样保留，保证保真（P-4）。
- **前端渲染**：虚拟滚动，只渲染可视区域附近的段落，22 万字也只绘制几十个段落。
- **AI 层**：BYOK，统一的模型适配层（见 2.6 节）。每个模型有一份"能力描述"（上下文、输出上限、思考档位、结构化输出），由拉取接口自动填充，上层按能力描述组装提示词和参数。
- **本地推理**：小模型用 ONNX Runtime 嵌入 Rust 后端运行（Windows 可用 DirectML 调 GPU，macOS 可用 CoreML），打包进安装程序即可，不依赖 Python。
- **存储**：SQLite 存文档元数据、批注、操作历史、审稿人画像；知识库见下节。

### 4.2 知识库方案（不易丢信息、容易找回）

政府文件的特点是**层级严格（章/条/款/项）、编号密集、措辞精确、同一概念多份文件交叉引用**。通用的"按固定长度切块 + 向量检索"最容易丢信息：切断条款、丢掉"第几条"的上下文、对文号和专有名词检索不准。

推荐方案：**结构化分块 + 父子检索 + 混合检索 + 重排**。

1. **按结构切分**：按标题和"第X条"切，每块保留完整路径（文件名 › 章 › 条），并带上文号、发文机关、日期等元数据。
2. **父子检索**：用小块（条/款）做检索保证精准，命中后返回它所在的整条或整节给模型，保证上下文完整。
3. **混合检索**：BM25 关键词检索（中文分词，对文号、专有名词、数字精确命中）+ 向量语义检索，两路结果合并。
4. **重排**：用重排模型对合并结果再排序，取前几条。
5. **原文可追溯**：每个结果都能跳回原文件的原始位置，AI 引用时显示出处。

建议选型（全部可嵌入桌面端本地运行，无需单独部署服务）：

| 组件 | 建议 | 理由 |
|---|---|---|
| 向量库 | LanceDB | 嵌入式、Rust 原生、磁盘存储，适合桌面 |
| 全文检索 | Tantivy + jieba 分词 | Rust 原生的 BM25，中文分词成熟 |
| 向量模型 | bge-m3 | 中文效果好，长文本支持好 |
| 重排模型 | bge-reranker-v2-m3 | 与 bge-m3 配套，中文效果好 |

后续可选：文件之间交叉引用多时，可在此基础上加一层**知识图谱（参考 LightRAG / GraphRAG）**，把"某文件引用/废止/修订了某文件"建成关系，回答跨文件问题。第一版不建议上，成本高、收益要等资料量上来才明显。

### 4.3 决策模型（Jev / Laya）

两者都是 2026 年出现的"决策模型"（System 1 模型）：不生成文字，只回答结构化问题，输出校准过的概率，速度比大语言模型快两个数量级。三种题型：是/否（noul）、单选/多选（choice）、打分（score）。

| | Jev | Laya |
|---|---|---|
| 来源 | TypeSafe AI，闭源 | 开源（Apache 2.0） |
| 使用方式 | 云端 API：Cloudflare Workers AI、OpenRouter（约 $0.042 / 百万输入 token） | 可本地运行，多语言版约 3.2 亿参数 |
| 上下文 | 32K | 多语言版最长 8K，实测约 4K 以内效果好 |
| 延迟 | 约 0.1 ~ 0.3 秒 | 约 33 毫秒（GPU） |
| 中文 | 未公布语言评测 | 支持 100+ 语言，但未单独公布中文成绩 |

**在本软件中的用法**：每条 AI 修改生成后，把"批注 + 原文 + 修改后文本 + 引用条款"交给决策模型，问一组固定问题，例如：

- 是/否：修改是否回应了批注提出的问题？
- 是/否：修改是否改变了原文的核心意思？
- 是/否：修改是否包含原文和引用资料中都没有的事实或数据？
- 打分：表述是否符合公文规范（1 ~ 5）？

各项概率按权重合成综合置信度，与阈值比较。每一项单独显示，用户能看到是哪一项拖了后腿。

**需要注意的风险（来自公开评测）**：

1. **Laya 零样本准确率不高**，公开评测显示需要用自己的数据微调后才能到生产可用水平；温度校准前概率偏自信。
2. **两者都没有公布中文评测**，需要我们用真实的中文批注样本先做一轮验证。
3. Laya 实际有效上下文约 4K，输入要控制在"批注 + 相关段落 + 修改"范围内，不能塞整章。

**应对方案**：

- 默认用 Jev（云端，零样本即可用）；本地/离线场景用 Laya。
- 用户每次"采纳 / 修改后采纳 / 拒绝"都记录下来，积累到一定量后，用这些数据**对本地 Laya 做温度校准和微调**，让打分越来越贴近用户自己的判断。这与第 2.3 节的审稿人画像是同一份数据，两者一起形成"越用越准"的闭环。
- 决策模型不可用或中文效果不达标时，可退回到用大语言模型当评审（LLM-as-Judge）。

## 5. 已确认的决策

| 问题 | 决定 |
|---|---|
| 决策模型 | Jev / Laya（见 4.3 节），**默认 Jev**，Laya 作为本地/离线选项 |
| 模型接入 | BYOK，四类模型由用户自配；小模型支持本地运行（见 2.6 节） |
| 写回方式 | **默认以修订（Track Changes）写回**，可切换为直接替换 |
| 支持格式 | **只支持 .docx**；.doc / .wps 请用户先另存为 .docx |
| 置信度阈值 | **默认 0.8**，可按审稿人单独调整 |
| 使用方式 | **单人本地使用**；审稿人画像和知识库支持导出/导入，便于换电脑 |
| 知识库规模 | 暂未知。设计上按"数千份文件、数千万字"留余量：增量索引、后台导入、可暂停 |

## 7. 第二批需求（v1.2，2026-09-29）

来源：用户 2026-09-29 的三条需求消息。本节是需求本身，实现方案见技术设计第 13 节。

### 7.1 知识库

| 编号 | 需求 | 说明 |
|---|---|---|
| K-7 | 普通 / 增强两种解析模式 | **普通模式**用内置解析：Word 段落和表格（表格每行写成“列名：值”，合并单元格补全）、有文字层的 PDF、TXT、Markdown。**增强模式**在设置里配置了 MinerU 或 PaddleOCR（百度 AI Studio）的 API 后启用，PDF 和图片交给在线服务做版面分析、表格识别和 OCR，扫描版 PDF 也能导入。设置页给出两家官网的注册和获取 Key 的链接；服务能查询额度时显示剩余额度，不能查询时说明“该服务不提供额度查询”并给出控制台链接。增强解析失败时自动退回普通模式，并在导入结果里说明原因 |

### 7.2 设置

| 编号 | 需求 | 说明 |
|---|---|---|
| S-1 | 外观放入设置 | 主题（浅色 / 深色 / Word 配色 / 跟随系统）从侧边栏底部移到设置 › 通用；侧边栏底部只留设置按钮 |
| S-2 | 关于与检查更新 | 设置 › 关于：显示当前版本、更新日志；“检查更新”查询 GitHub 最新发布版，有新版时显示版本号、更新内容和下载链接（用默认浏览器打开） |
| S-3 | 数据备份 | 设置 › 数据：一键把知识库（资料原件、索引、向量）和审稿人（审稿人、署名映射、案例、画像）导出为一个备份文件；导入时可选“合并到当前数据”或“替换当前数据”（替换前自动备份当前数据）。备份里不含 API Key |

### 7.3 批注栏

| 编号 | 需求 | 说明 |
|---|---|---|
| C-1 | 切换批注时重置选区 | 切换到另一条批注时清除正文里的选中文字，避免把上一条批注时选的范围误用到新批注上 |
| C-2 | 只展开选中的批注 | 未选中的批注折叠为一行（作者、批注首句、状态和修复进度）；点击后展开，同时只展开一条 |
| C-3 | 回复批注 | 每条批注下有“回复”按钮，输入内容后写入 Word 批注回复（作者为设置中的修订作者），可撤销 |
| C-4 | 两种排版 | **密集列表**（现在的方式）和**经典 Word 模式**：批注显示在正文右侧页边，与所批注的文字处于同一高度，随正文滚动，滚过去就看不到。在设置 › 通用和批注栏标题处切换 |

### 7.4 AI 修复

| 编号 | 需求 | 说明 |
|---|---|---|
| A-10 | “待补充”不能直接应用，改为联网查找 | AI 修改里含有“【待补充：…】”这类占位时，不允许一键应用。卡片上显示“查找资料”：按占位要补充的内容联网搜索，列出几条可点击的结果（用默认浏览器打开）；结果是可直接下载的文件（PDF、Word 等）时，显示“下载至知识库”，下载后自动解析入库，之后可重新生成。只有用户手动把占位改成实际内容后，才允许应用到原文。搜索优先用大语言模型自带的联网能力；模型不能联网时，降级为本机按白名单抓取政府和标准网站（白名单见技术设计 13.8，可在设置中编辑） |
| A-11 | AI 重写 | “AI 修复”旁增加“AI 重写”。AI 修复只改批注指出的问题、改动越小越好；AI 重写用于原文本身就不对的情况，可以整段重写（仍不得编造数据和文件） |
| A-12 | 修改方向 | 批注卡片上有可编辑的“修改方向”输入区。生成前填写，引导 AI 往正确方向改；发现 AI 改错时，修正方向后重新生成。修改方向在提示词中优先于其他要求（安全和不编造的规则除外） |

### 7.5 文档校对

区别于按批注修复：这是交稿前（首次提交或最终提交）对整份文档的自查。

| 编号 | 需求 | 说明 |
|---|---|---|
| Q-1 | 错别字 | 错字、别字、多字漏字、的地得、常见公文用词错误 |
| Q-2 | 序号错误 | 各级标题和列表序号跳号、重号、同级混用不同样式（如“一、”和“1.”混用）、括号全半角不统一 |
| Q-3 | 前后不一致、前后矛盾 | 同一指标（总投资、面积、规模、工期、日期、单位名称等）在不同位置数值或说法不同；前文结论与后文矛盾 |
| Q-4 | 张冠李戴 | 项目要素（项目名称、所在区县、建设单位等）写错，例如崇明区项目中出现“浦东新区” |
| Q-5 | 格式问题 | 多余空格、连续空行、全半角标点混用、括号引号不配对、重复标点 |
| Q-6 | 引用文件时效 | 找出书名号内的法律法规、标准规范、政策文件及标准编号，联网核查是否已废止或有新版本；有新版本时提示更新，确认后下载新版入知识库，并按新版检查文中引用的条款和表述 |
| Q-7 | 校对策略与报告 | 先按规则做本地检查，再用大语言模型分段检查，最后汇总去重。结果按类别和位置列出，点击定位到原文，可逐条“应用”（写为修订）或“忽略”；可只校对当前章节；未改动的段落再次校对时复用上次结果 |

### 7.6 本批说明

- 知识库原有的 Word 表格按行分块（每行带列名、合并单元格补全）属于普通模式，已完成。
- MinerU、PaddleOCR 两家接口按官方公开的客户端代码实现（见技术设计 13.2）；开发环境无法访问两家服务，需用真实 Key 在设置里点“测试”核对。
